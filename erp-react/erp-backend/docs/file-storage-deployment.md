# File storage — production paths, configuration and persistence

This document records where the ERP keeps runtime files, which components touch
each path, what must be configured for a production deployment, and what is
guaranteed to survive a restart. It is the companion to
[upload_pipeline.md](upload_pipeline.md) (limits and the request path) and
[database-deployment.md](database-deployment.md) (reference data).

## 1. What is stored

The upload root (`app.upload.dir`, default `uploads`) holds real user documents
and runtime files. It is **data**, not build output: it must be treated with the
same care as the MySQL database.

```
<ERP_UPLOAD_DIR>/                        # app.upload.dir — the single root
├── <uuid>.pdf|png|step|…                # uploaded documents and attachments (server-generated UUID names)
├── models/                              # app.storage.models — CAD model originals
│   ├── <MODEL-NO>_<8-hex>.step|sldprt|…
│   └── cache/                           # model-derived cache artefacts
├── drawings/                            # app.storage.drawings — drawing originals
├── cad-previews/                        # app.cad.worker.preview-dir — generated preview GLBs
└── processing-jobs/                     # staged inputs of asynchronous bulk jobs (temporary)
```

Measured on the developer copy of the repository at the time of this audit:

| Location | Contents | Size |
|---|---|---|
| upload root | 186 uploaded files (pdf, png, jpg, txt, …) | 259 MB total |
| `models/` | 43 CAD model files | 7.0 MB |
| `drawings/` | 19 drawing files | 476 KB |
| `cad-previews/` | 1 preview GLB | 304 KB |
| `processing-jobs/` | empty (staging only, swept after completion) | 0 |

Every uploaded name is generated by the server (`FileStorageService` stores
`UUID.ext`, `ModelService`/`DrawingService` store `<NUMBER>_<8-hex>.ext`); the
user-supplied file name never becomes a path. Existing data was not moved,
renamed or deleted during this audit.

## 2. Who reads and writes the upload root

| Path | Written by | Read by |
|---|---|---|
| upload root | `FileStorageService.store()` / `storeBytes()` — used by ~20 module services (leads, customers, quotations, sales orders/contracts, invoices, credit notes, payment receipts, delivery challans, purchase requisitions/RFQs, CPR, cost workout, follow-ups, questionnaire, expense trips, marketing map, production attachments) and `DocumentRepositoryService` | `FileStorageService.loadAsResource()` via `FileController` `GET /v1/files/{name}` (authenticated), `DocumentReconciliationService` (existence/size checks, `listRootFiles()`) |
| `models/` | `ModelService.saveFile()` (multipart model upload, replacement upload) | `ModelService.getFilePath()` → `GET /v1/models/{id}/viewer`, `/download`, `/preview`, `/3d`; `ModelService.deleteFile()` on reject/delete |
| `drawings/` | `DrawingService.saveFile()` | `DrawingService` download; `deleteFile()` on delete/replace |
| `cad-previews/` | `CadJobWorker` (writes `<base>_<hash>.glb`) | `CadJobWorker.cleanUnreferencedPreviews()` (retention), `GET /v1/models/{id}/3d` when a model points at a preview GLB |
| `processing-jobs/` | `ProcessingJobInputStore` (stages bulk-extraction inputs) | `ProcessingJobInputStore.resolveInput()` during the job; `deleteInputs()` / `sweepOrphans()` afterwards |
| multipart spool (`ERP_UPLOAD_TEMP_DIR`) | Tomcat, before the controller runs | discarded after the stored copy is written |

`UploadStorageConfig` only prepares the multipart spool directory at startup and
fails fast if it cannot be created. `AttachmentStorageService` never touches the
disk: the shared 4 GB pool is a **database ledger** over the eight attachment
tables, reconciled at startup and daily by `AttachmentStorageReconciliationJob`.

### What deletes anything

Nothing deletes uploads at startup or on restart. The only deletions in the code
base are:

1. **Processing-job staging** — the job's own `processing-jobs/<ref>` directory,
   after the job finishes, plus orphan staging directories older than
   `app.processing-jobs.retention-hours`.
2. **CAD worker staging** — `<temp-root>/<jobId>` after conversion, plus
   orphaned directories older than `app.cad.worker.temp-retention-hours`.
3. **Unreferenced preview GLBs** older than `app.cad.worker.preview-retention-hours`
   that no model row points at.
4. **Explicit business actions** — deleting/replacing a model or drawing, and
   document deletion initiated by an authorised user.

None of these ever walks the upload root or removes files it does not own.

## 3. Production configuration

`ERP_UPLOAD_DIR` is the one switch that must be set. Every persistent storage
root derives from `app.upload.dir`, so one variable moves all of them onto the
same external volume:

| Property | Environment variable | Default | Purpose |
|---|---|---|---|
| `app.upload.dir` | `ERP_UPLOAD_DIR` | `uploads` | upload root (documents, attachments) |
| `app.storage.models` | `ERP_MODEL_STORAGE_DIR` | `${app.upload.dir}/models` | CAD model originals |
| `app.storage.drawings` | `ERP_DRAWINGS_STORAGE_DIR` | `${app.upload.dir}/drawings` | drawing originals |
| `app.cad.worker.preview-dir` | `ERP_CAD_WORKER_PREVIEW_DIR` | `${app.upload.dir}/cad-previews` | generated preview GLBs |
| `spring.servlet.multipart.location` | `ERP_UPLOAD_TEMP_DIR` | `${java.io.tmpdir}/erp-upload-spool` | multipart spool (transient) |
| `app.cad.worker.temp-root` | `ERP_CAD_WORKER_TEMP_ROOT` | `${java.io.tmpdir}/cad-jobs` | CAD staging (transient, intentionally NOT persistent) |
| `spring.servlet.multipart.file-size-threshold` | `ERP_UPLOAD_DISK_THRESHOLD` | `0B` | parts always go to disk, never the heap |

```bash
# Absolute path, on a volume that is mounted before the process starts.
export ERP_UPLOAD_DIR=/var/lib/erp/uploads
# Spool volume: two copies of a large upload exist at once (spool + stored copy).
export ERP_UPLOAD_TEMP_DIR=/var/lib/erp/upload-spool
```

Rules for production:

- **Absolute path only.** A relative default resolves against the process
  working directory; a service manager or container restart can change it, which
  would strand the data behind a directory the operator never sees.
- **Create and chown the directory first.** `FileStorageService` creates the
  root at startup and fails startup if it cannot.
- **Size the volume** for the configured shared attachment pool
  (`ERP_ATTACHMENT_POOL_BYTES`; the default is 4 GB) plus the CAD model and
  drawing libraries; size the spool volume for
  `max-request-size × concurrent uploads` (see [upload_pipeline.md](upload_pipeline.md)).
- **Use the same volume for the ERP and the isolated CAD worker.** Both processes
  must see the same `ERP_UPLOAD_DIR`; otherwise a converted preview is written to
  a path the ERP cannot read.
- **Per-directory overrides exist** (`ERP_MODEL_STORAGE_DIR`,
  `ERP_DRAWINGS_STORAGE_DIR`, `ERP_CAD_WORKER_PREVIEW_DIR`) for layouts that
  genuinely need them. Setting one moves *new* files only: model and drawing rows
  store an absolute `file_path`, so existing rows keep resolving where they were
  written.

### Historical note

Before this change, `app.storage.models` and `app.storage.drawings` were not
declared in `application.properties` at all and fell back to annotation defaults
of `./uploads/models` and `./uploads/drawings` — working-directory-relative and
**not** covered by `ERP_UPLOAD_DIR`. Pointing only `app.upload.dir` at an
external volume therefore split storage in two, leaving model and drawing
originals on whatever ephemeral filesystem the process happened to start from.
The defaults now derive from `app.upload.dir`, which for an unset `ERP_UPLOAD_DIR`
still resolves to `uploads/models` and `uploads/drawings` — the layout every
existing development checkout already uses.

## 4. Restart persistence

Verified by end-to-end test (see §6): the upload root lives entirely outside the
build output, nothing writes to it during startup, and the only scheduled jobs
that touch files are the staging/preview sweeps described in §2. A restart
therefore leaves uploaded documents, CAD model originals and generated previews
intact and reachable through their authenticated endpoints.

Consequences of that design:

- **The volume must outlive the process.** Never point `ERP_UPLOAD_DIR` at a
  directory inside a container image layer, a build directory or `target/`.
- **Uploads are not in Git and not in the jar.** The repository `.gitignore`
  carries `uploads/` (covering both `erp-backend/uploads/` and the root
  `uploads/`), `git ls-files` reports no file under it, and the packaged jar
  contains no `uploads/` entry — so a fresh checkout or a fresh build never
  creates or overwrites user data.
- **Back it up like the database.** A consistent backup is the upload volume
  plus a `mysqldump` of `erp_db`; restoring files without the row that points at
  them (or vice versa) leaves orphans, which `DocumentReconciliationService`
  reports rather than repairs.

## 5. Serving files

`GET /v1/files/{storedName}` is authenticated (`@PreAuthorize("isAuthenticated()")`
in `FileController`), enforces the server-generated name format, and additionally
enforces document-repository visibility when the file is owned by a document row.
Content is served with `X-Content-Type-Options: nosniff` and forced
`Content-Disposition: attachment` for anything not in a small inline allowlist.
CAD originals are served only through
`GET /v1/models/{id}/viewer`, `/download`, `/preview` and `/3d` (the last two are
for the browser-renderable representation: `/preview` when no conversion is
needed, `/3d` once the CAD worker has produced a GLB).
The frontend always requests files through the authenticated client
(`src/utils/fileAccess.js`, `src/services/documentService.js`), never as a bare
public URL.

## 6. Verification performed

```bash
cd erp-backend
./mvnw -o -B test -Dtest='StorageRootConfigurationTests,FileStorageSecurityTests,\
FileSecurityTests,UploadStreamsTests,UploadSizeGateFilterTests,\
Drawing2DFormatSupportTests,AttachmentStorageLedgerTests'
```

85 tests, all passing. `StorageRootConfigurationTests` locks the wiring: it
resolves the shipped placeholders and fails the build if any storage root drifts
back to a working-directory path.

Runtime check against a scratch database with `ERP_UPLOAD_DIR` pointed at an
external directory:

1. `POST /v1/documents/upload` → file lands in `<ERP_UPLOAD_DIR>/<uuid>.txt`.
2. `POST /v1/models` with a `.step` file → lands in `<ERP_UPLOAD_DIR>/models/`,
   while the repository-local `uploads/models/` count is unchanged.
3. Model row records the absolute path under `ERP_UPLOAD_DIR`.
4. `GET /v1/files/{name}` and `GET /v1/models/1/download` → `200`, correct bytes;
   the same request without a token → `401`.
5. Restart the process → both files still present on disk and both endpoints
   still return `200`.
